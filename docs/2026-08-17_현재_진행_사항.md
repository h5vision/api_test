## 1. 현재 목표

Vision Backend는 VS Code Code Assistant, AI Server, RAG/VectorDB와 Git
Snapshot을 연결하는 FastAPI Control Plane으로 구성되어 있습니다.

현재 우선 목표는 다음과 같습니다.

1. 다른 PC에서 저장소를 clone한 뒤 Docker Compose로 동일하게 기동할 수 있을 것
2. 내부망 VS Code Client가 관리자 수동 IP 등록 없이 첫 Chat에서 자동 등록될 것
3. 관리자가 AI 모델, VectorDB, Embedding과 Project Route를 UI에서 설정할 것
4. Frontend 요청, AI 추론, Snapshot 비교와 인덱싱 상태를 관리자 로그에서 추적할 것
5. 기존 공개 API와 OpenAPI 계약을 유지하면서 내부 소유 구조를 분리할 것

## 2. 완료된 구조 개선

### Backend 리팩터링

Phase 0~17 리팩터링을 완료하고 다음 경계를 canonical owner로 분리했습니다.

- FastAPI public app composition과 API Router
- Chat intake, context, routing, streaming과 progress
- Generation catalog, provider routing과 AI Server adapter
- Retrieval, RAG와 외부 VectorDB adapter
- Admin Router와 관리자 전용 API 경계
- Schema domain 분리와 legacy compatibility facade
- 테스트 경로 정렬, 중복·obsolete 파일 정리

리팩터링 이후 기존 기능 회귀 없이 테스트와 OpenAPI 불변성을 확인한 상태에서
`main` 기준 구조로 전환했습니다.

### Docker 이식성

- Windows 11 + WSL2 Docker 환경을 기준으로 Compose를 정리했습니다.
- 프로젝트 경로를 `PROJECT_PATH` bind mount로 주입합니다.
- PostgreSQL, Redis, Qdrant와 Runtime secret은 Docker volume에 보존합니다.
- Migration과 Python dependency 준비가 API 시작 전에 완료됩니다.
- Traefik은 기본적으로 Host의 `0.0.0.0:80`, `0.0.0.0:8000`에 공개됩니다.
- 관리자 Preview는 Host의 `127.0.0.1:4180`에만 공개됩니다.
- 사용 중인 Granian 기반 이미지는 원격 manifest 조회가 가능한 상태입니다.

### Client 자동 등록

- 최초 `POST /v1/chat` 요청에서 미등록 VS Code Client를 자동 등록합니다.
- 서버가 생성한 `X-Client-ID`와 자동 등록 여부를 응답 Header로 반환합니다.
- 식별 우선순위는 Client ID → Instance ID → 원본 IP fallback입니다.
- Frontend IP를 Runtime Network 설정에 미리 입력하지 않아도 됩니다.
- 모델·언어 discovery API는 전체 Runtime 설정 완료 전에도 조회할 수 있습니다.
- 관리자가 Client를 `enabled=false`로 전환하면 이후 요청을 `403`으로 차단합니다.
- 등록·식별·최초 연결 과정은 관리자 통신/등록 로그에 기록됩니다.

### AI 모델 운영

- Ollama, OpenAI-compatible, Cloud Provider를 관리자 페이지에서 등록할 수 있습니다.
- IP/Host+Port 또는 Base URL 방식 모두 지원합니다.
- 인증 없음, Bearer, X-API-Key 형식을 지원합니다.
- Provider 저장 후 Chat/Embedding 모델을 자동 감지할 수 있습니다.
- Local, Remote Runtime, Cloud 배포 위치를 구분합니다.
- Vision managed와 Provider managed Chat 처리 책임을 선택할 수 있습니다.
- 감지된 모델 중 관리자 기본 Chat 모델을 선택합니다.

### VectorDB·Embedding·Index

관리자 개요의 Vector 설정을 다음 단계로 분리했습니다.

1. VectorDB 연결 Host/Port
2. Embedding 실행 위치, Provider, Base URL과 실제 모델
3. Vector Dimension, Batch, Collection과 Index version
4. 프로젝트별 verified binding 조회와 active Route 선택
5. Repository 재인덱싱, 외부 Artifact와 Indexing Job 상태 확인

Vision 기본 Qdrant는 선택적으로 사용할 수 있고 외부 Qdrant-compatible Target도
등록할 수 있습니다. VectorTarget, EmbeddingProfile과 Project Route는 PostgreSQL
Runtime registry를 authority로 사용합니다.

### Repository·Snapshot

- Public GitHub Commit Snapshot Control Plane을 구현했습니다.
- Repository와 실제 Git Commit SHA를 기준으로 Snapshot을 식별합니다.
- Snapshot Locator, Tree와 UTF-8 파일 원문을 관리자 화면에서 조회합니다.
- Snapshot compare는 `same`, `different`, `unknown`과 workspace 상태를 반환합니다.
- Snapshot manifest/file Hydration API와 hash 검증을 제공합니다.
- External Project Registry와 RAG project reconciliation 기반을 추가했습니다.
- 임의 생성 SHA를 Git Commit SHA로 사용하지 않습니다.

### 관리자 페이지

관리자 페이지는 다음 네 Route로 구분됩니다.

| Route | 용도 |
|---|---|
| `/` | Client, AI Provider, 기본 모델, VectorDB와 Runtime 설정 |
| `/system-status` | Endpoint, 통신, Client 등록, Chat 감사와 Queue 상태 |
| `/snapshots` | Repository 등록, Commit Snapshot, Tree와 파일 조회 |
| `/playground` | 모델·프로젝트 선택, Streaming Chat, 첨부와 Citation 검증 |

README에 최초 실행부터 각 입력 필드, 정상 판정과 장애 확인까지 관리자 사용
가이드를 추가했습니다.

## 3. 주요 공개 API 상태

| API | 현재 역할 |
|---|---|
| `GET /v1/health` | Process와 Runtime/외부 서비스 상태 조회 |
| `GET /v1/models` | 사용 가능한 Chat/Embedding 모델 catalog 조회 |
| `POST /v1/chat` | Client 자동 등록, 입력 정규화, 모델 라우팅과 SSE/JSON 응답 |
| `POST /v1/chat/contexts` | 별도 Canonical Context 등록 |
| `POST /v1/snapshots/compare` | Project/Snapshot/Commit 상태 비교 |
| `GET /v1/IngestResponse` | Backend에 알려진 프로젝트/인덱싱 상태 목록 |
| `POST /v1/documents/ingest` | 프로젝트 문서 인덱싱 접수 |
| `GET /v1/contracts/chat-stream` | SSE event 계약 조회 |
| `GET /v1/citations/{request_id}/{citation_id}` | Citation 원문 재조회 |

Frontend는 관리자 API나 VectorDB를 직접 호출하지 않고 공개 FastAPI 계약만
사용합니다. 관리자 API는 `/admin-api/*` Nginx 경로를 통해서만 사용합니다.

## 4. 완료된 검증

기능 커밋 `a329c90` 기준 검증 결과입니다.

```text

Fresh Docker DB smoke     PASS
git diff --check          PASS
```

Fresh Docker 환경에서 확인한 흐름은 다음과 같습니다.

1. 새 PostgreSQL/Redis/Qdrant volume 생성과 migration 완료
2. Runtime 설정 전 `GET /v1/models` 응답 `200`
3. 첫 Chat 요청에서 Frontend Client record 생성
4. 응답 Header의 `X-Client-ID`, `X-Client-Auto-Registered: true` 확인
5. Runtime 미설정 인덱싱 요청은 `503 RUNTIME_CONFIGURATION_REQUIRED` 반환
6. Frontend 필드 없이 BackendAI Network 대상 저장 `200`
7. 관리자 UI build와 Nginx 관리자 API Proxy 응답 확인

새 설치 smoke test에는 실제 AI 모델을 등록하지 않았으므로 Chat 생성 결과는
`MODEL_NOT_AVAILABLE`이었습니다. 이 응답에서도 Client 자동 등록과 ID 발급은
정상적으로 완료되는 것을 확인했습니다.

- Draft PR #1 review와 `main` 병합
- 다른 PC에서 실제 clone 후 `docker compose up -d` 재검증

- 관리자 기본 Chat 모델 선택 후 실제 Frontend Chat 왕복
- 운영 VectorDB에 맞는 Vector Dimension과 Collection 확인

- Private Git Repository 인증 방식 확정
- 외부 RAG Server의 `/projects`, `/search`, `/prompt` 최종 계약 검증

## 7. 인계용 명령

```powershell
git clone https://github.com/h5vision/api_test.git
cd api_test
Copy-Item compose.env.example compose.env
docker compose --env-file compose.env config --quiet
docker compose --env-file compose.env up -d
docker compose --env-file compose.env ps -a
```

상태 확인:

```powershell
Invoke-RestMethod http://127.0.0.1:8000/v1/health
Invoke-WebRequest -UseBasicParsing http://127.0.0.1:4180/
docker compose --env-file compose.env logs --tail 100 migrate api admin-web
```

내부망 Client는 `<SERVER_IP>:8000`의 공개 API를 사용하고, 관리자는
`http://<SERVER_IP>/` 또는 서버 로컬의 `http://127.0.0.1:4180/`을 사용합니다.
